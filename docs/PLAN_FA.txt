دستور ساخت نرم‌افزار آفلاین فروشگاه مواد غذایی و ادویه
نسخه برنامه‌ریزی ۱ | مخاطب Codex یا Claude | تاریخ ۲۰۲۶/۱۰/۱۰

این متن را به عامل کدنویسی بدهید. این فایل مشخصات ساخت است؛ هنوز برنامه‌ای ساخته، نصب یا روی دستگاه واقعی آزمایش نشده است. هدف، کمک به بابک برای فروشگاه برادرش در بابلسر است. فروشگاه نزدیک افتتاح است؛ رایانه، ترازو و کارت‌خوان هنوز خریداری نشده‌اند و مدل بارکدخوان و چاپگر نیز مشخص نیست.

۱ هدف و مرز پروژه

یک برنامه ساده، فارسی و قابل‌اعتماد برای یک فروشگاه، یک رایانه و یک انبار بساز. اولویت با فروش روزانه، خرید، موجودی، دخل‌وخرج، سود ناخالص، بدهی تأمین‌کننده و نسیه مشتری است. حسابداری رسمی، مالیات، سامانه مؤدیان، حقوق‌ودستمزد، چندشعبه، فروش اینترنتی، اپ موبایل، اتصال ابری و همگام‌سازی خارج از محدوده‌اند. گزارش‌ها ابزار مدیریتی‌اند و ادعای انطباق مالیاتی یا صورت‌های مالی رسمی نکن.

فرض اولیه سیستم‌عامل Windows و مرورگر محلی است؛ این فرض را در README ثبت کن. نبود مدل سخت‌افزار نباید ساخت هسته را متوقف کند. وزن و مبلغ کارت در نسخه اولیه دستی‌اند. رابط کاربری باید برای استفاده روزانه فرد غیرمتخصص مناسب باشد. اطلاعات واقعی مشتری، شماره کارت یا داده فروشگاه را در مخزن، آزمون و گزارش اشکال قرار نده.

۲ فازها و ترتیب اجرا

فاز صفر: اسکلت پروژه، migration، تنظیمات، ورود، قواعد ریال و وزن، سرویس تراکنش، داده آزمایشی، آزمون پایه و نمونه اجرای محلی.

فاز یک: کالا، قیمت، خرید، موجودی، فروش نقدی/کارت دستی، وزن دستی، بارکدخوان کیبوردی، چاپ HTML فارسی، گزارش فروش و سود. امکان فنی backup از همین فاز وجود داشته باشد. این فاز به‌تنهایی نسخه نهایی افتتاح نیست.

فاز دو: نسیه، بدهی تأمین‌کننده، پرداخت بخشی، مرجوعی فروش و خرید، هزینه، بستن روز، مدیر/صندوقدار، backup/restore آزمایش‌شده و بسته اجرایی. نسخه آزمایشی قابل استفاده فروشگاه، مجموع فازهای صفر تا دو است؛ نسیه و مرجوعی را به آینده نامعلوم موکول نکن. فوریت افتتاح مجوز استفاده واقعی از نمونه ناقص نیست؛ عبور از آزمون‌های حیاتی الزامی است.

فاز سه: آداپتور واقعی ترازو، چاپگر و کارت‌خوان فقط پس از دریافت مدل، روش اتصال، مستندات و دستگاه آزمایشی. برای شروع فقط interface و mock بساز. هیچ ارتباط بانکی فرضی یا موفقیت ساختگی نساز.

در پایان هر مرحله، نتیجه آزمون، محدودیت باقی‌مانده و دستور اجرای قابل تکرار را بنویس؛ علامت «انجام شد» فقط برای کار واقعاً آزمایش‌شده مجاز است.

۳ معماری و اجرای آفلاین

Python + FastAPI + SQLAlchemy + Alembic + SQLite انتخاب اصلی است. UI با Jinja2، HTMX محلی و JavaScript محدود باشد؛ Node، React، Docker و سرویس جداگانه لازم نیست. نسخه‌های پایدار و سازگار را هنگام ساخت از منابع رسمی بررسی و دقیق قفل کن؛ عبارت مبهم latest در وابستگی‌ها نگذار.

یک فرآیند برنامه و یک worker، فقط روی 127.0.0.1 با پورت مشخص اجرا شود؛ launcher مرورگر را باز کند. اجرای دوم همان برنامه باید صفحه موجود را باز کند، نه سرور/نویسنده دوم. قالب، CSS، فونت فارسی مجاز، HTMX و tzdata داخل بسته باشند. اجرای روزمره هیچ وابستگی به اینترنت، CDN، API ابری یا telemetry ندارد.

ساختار پیشنهادی: app/domain برای محاسبات خالص؛ services برای posting و گزارش؛ db برای مدل و migration؛ web برای route/template؛ adapters برای سخت‌افزار؛ tests؛ scripts؛ packaging؛ docs. منطق قیمت، سود و موجودی را در route یا JavaScript ننویس. مسیر DB، backup و log از پوشه executable جدا و قابل نمایش در تنظیمات باشد؛ داده در پوشه موقت PyInstaller یا Program Files ذخیره نشود.

SQLite برای این استفاده محلی با نویسندگی محدود مناسب است [۱]. فایل فعال را روی دیسک محلی نگه دار، نه NAS، پوشه شبکه یا مسیر همگام‌سازی ابری. برای هر اتصال foreign_keys=ON، busy_timeout=5000 و synchronous=FULL اعمال و journal_mode=WAL را هنگام راه‌اندازی بررسی کن [۲]. این تنظیم‌ها جای UPS و backup را نمی‌گیرند.

۴ قواعد قطعی پول و مقدار

تمام پول نهایی، بدهی، پرداخت و ارزش موجودی در DB، INTEGER ریال است. UI پیش‌فرض تومان با برچسب دائمی واحد؛ هر تومان دقیقاً ۱۰ ریال. مبلغ کارت‌خوان نیز واحد صریح داشته باشد. ورودی تومان حداکثر یک رقم اعشار می‌پذیرد تا ریال کامل حاصل شود؛ اعشار بیشتر رد شود. نمایش ۱۰۱ ریال باید ۱۰٫۱ تومان باشد، نه ۱۰ تومان. از float و SQLite REAL برای پول استفاده نکن.

کالای وزنی، qty_base صحیح برحسب میلی‌گرم: ۱ گرم = ۱۰۰۰ و ۱ کیلوگرم = ۱۰۰۰۰۰۰ میلی‌گرم. زعفران ۰٫۱۲۵ گرم دقیقاً ۱۲۵ میلی‌گرم است. کالای تعدادی، qty_base صحیح برحسب عدد دارد و مقدار کسری نمی‌پذیرد. هر کالا quantity_step متناسب با روش فروش دارد؛ qty_base مثبت و مضرب صحیح quantity_step باشد. دقت ثبت از دقت واقعی ترازو بیشتر نباشد. تغییر نوع واحد بعد از گردش ممنوع؛ بسته‌بندی مستقل در نسخه اول SKU جدا باشد.

قیمت فروش به‌صورت unit_price_rial و price_basis_qty ذخیره شود، مثلاً قیمت یک کیلو یا یک گرم. مبلغ ردیف = ROUND_HALF_UP(price × qty / basis). تخفیف فقط مبلغ ثابت هر ردیف، بین صفر و مبلغ ناخالص؛ تخفیف سراسری/درصدی فعلاً لازم نیست. مبلغ سند جمع مبالغ نهایی ردیف‌هاست. فروش رایگان فقط با تأیید مدیر و علت؛ ردیف Payment صفر نساز؛ فروش رایگان/کاملاً نسیه می‌تواند بدون Payment ثبت شود و مقدار کالا مثبت است.

برای محاسبات میانی Decimal با precision=50 و ROUND_HALF_UP استفاده کن [۳]. تبدیل از رشته/عدد صحیح باشد، هرگز از float. سقف‌های ورودی و overflow در INTEGER 64-bit را پیش از SQL کنترل کن.

۵ بهای تمام‌شده و سود

منبع معتبر هر کالا دو مقدار است: Q موجودی صحیح و V ارزش موجودی صحیح ریال. میانگین موزون جاری = Decimal(V)/Q؛ میانگین نمایشی گرد‌شده منبع محاسبه نیست. خرید با مقدار q و بهای خالص v باعث Q+=q و V+=v می‌شود. هزینه حمل جداگانه در نسخه اول هزینه دوره است و خودکار روی کالا پخش نشود.

در فروش q، بهای خروج = ROUND_HALF_UP(V×q/Q). اگر q=Q، دقیقاً کل V خارج شود تا با موجودی صفر، ارزش صفر شود. بهای کل خروج و مقادیر Q/V پیش از خروج را روی ردیف/حرکت ثبت کن. خرید بعدی نباید سود فروش گذشته را تغییر دهد. خروج بیش از موجودی همیشه ممنوع است؛ موجودی یا ارزش منفی مجاز نیست.

سود ناخالص = فروش خالص پس از مرجوعی − بهای تمام‌شده فروش پس از برگشت بهای مرجوعی. «نتیجه عملیاتی ساده» = سود ناخالص − هزینه دوره − ضایعات و تعدیل کاهشی + تعدیل افزایشی + purchase_return_variance؛ این سود خالص رسمی نیست. هزینه دوره، ضایعات/تعدیل انبار را شامل نشود؛ هر مؤلفه فقط یک‌بار وارد شود و موجودی افتتاحیه تعدیل سودآور محسوب نشود. خرید موجودی هزینه فوری فروش نیست؛ پرداخت بدهی و دریافت نسیه نیز درآمد/هزینه جدید نیستند. سرمایه‌گذاری مالک، برداشت مالک و مغایرت صندوق جدا گزارش شوند.

۶ مدل داده محدود و صریح

شناسه‌ها UUID یا INTEGER پایدار؛ timestamps به UTC؛ مبلغ‌ها و مقدارها integer؛ اسناد قطعی غیرقابل حذف. حداقل موجودیت‌ها:

- Product: id, sku UNIQUE, name, normalized_name, kind(weight/count), quantity_step, active, min_stock. ProductBarcode: product_id, code TEXT UNIQUE؛ صفرهای اول حفظ شود.
- Price: product_id, unit_price_rial, basis_qty, version, changed_at, changed_by؛ تاریخچه تغییر نگه داشته شود.
- Party: id, name, normalized_name, customer_enabled, supplier_enabled, phone اختیاری، active. اطلاعات غیرضروری نخواه.
- Document: id, kind(sale/purchase/sale_return/purchase_return/opening/adjustment/expense), number UNIQUE، party_id، status(draft/posted/cancelled)، accounting_date، created_at، posted_at، actor_id، version، net_rial، reason و reference_document_id.
- DocumentLine: document_id, line_no، product_id، qty_base، unit_price_rial، basis_qty، discount_rial، net_rial، original_line_id برای مرجوعی، cost_rial و snapshot نام/واحد/قیمت. UNIQUE(document_id,line_no).
- StockBalance: product_id PRIMARY KEY، qty_base>=0، value_rial>=0، version. CHECK موجودی صفر مستلزم ارزش صفر.
- StockMovement: product_id، document_line_id، type، qty_delta، value_delta، quantity_after، value_after، sequence، created_at؛ UNIQUE(document_line_id,type). این دفتر، تاریخچه اصلی مقدار و ارزش است؛ balance یک خلاصه کنترل‌شونده است.
- PartyEntry: party_id، document_id، bucket(AR/AP/customer_refund_due/supplier_refund_due)، signed_amount_rial، accounting_date، source_payment_id یا source_allocation_id برای تسویه و event_key UNIQUE. هر اثر دقیقاً یک رویداد منشأ دارد. افزایش طلب/بدهی مثبت و کاهش منفی؛ entries تغییرناپذیر و مانده هر bucket غیرمنفی.
- MoneyAccount: id، name، kind(cash/card_clearing/bank)، active. MoneyMovement: account_id، payment_id، signed_amount_rial، category، accounting_date، actor_id. مانده از گردش‌ها محاسبه شود.
- Payment: id، party_id اختیاری، direction، amount_rial>0، account_id، status، external_ref اختیاری، occurred_at، accounting_date، actor_id. فقط وضعیت تأییدشده گردش پول ایجاد کند.
- SettlementAllocation: source_payment_id یا source_credit_document_id، target_entry_id اشاره به PartyEntry بدهکار/بستانکار اولیه، bucket، amount_rial>0؛ دقیقاً یک منبع. تخصیص اضافه به مبلغ منبع یا بدهی هدف ممنوع؛ انتقال پول و کاهش بدهی نباید دوبار ثبت شوند.
- PaymentAttempt: request_key UNIQUE، invoice_id، requested_amount_rial، state، external_ref، updated_at؛ هیچ شماره کامل کارت، PIN یا CVV ذخیره نشود.
- DailyClose: accounting_date UNIQUE، expected_cash، counted_cash، difference، closed_by، closed_at، note.
- User و Session: username UNIQUE، password_hash، role، active؛ session_token_hash، expires_at، user_id.
- AuditEvent، IdempotencyRecord و BackupRecord: عامل/عمل/مرجع/زمان/علت؛ کلید یکتا و payload_hash و result_id؛ مسیر/هش/schema/version/نتیجه آخرین backup و restore-test.

PartyEntry حاصل رویدادهای سند و تخصیص است؛ در یک تراکنش ساخته شود و مستقیم قابل ویرایش نباشد. همه جدول‌ها id پایدار دارند؛ کلید هر اثر (منشأ+نوع اثر+طرف/حساب) یکتا باشد؛ یک رویداد می‌تواند چند اثر اتمیک داشته باشد. constraint، FK با RESTRICT و CHECK نوع integer/محدوده‌ها داشته باش؛ قوانین جمعی بین ردیف‌ها داخل سرویس تراکنشی بررسی شوند. index روی accounting_date/status، party_id/date، product_id/sequence، original_line_id، reference_document_id و کلیدهای خارجی گزارش‌پذیر بساز.

۷ قطعی‌کردن و جلوگیری از ثبت دوباره

draft هیچ اثر مالی یا انباری ندارد. posted قابل ویرایش/حذف نیست؛ اصلاح با سند برگشتی و علت انجام می‌شود. cancelled فقط برای پیش‌نویس است. وضعیت paid/partial/unpaid و partly_returned/fully_returned از گردش‌ها مشتق شود، نه تغییر مخفی سند اصلی. trigger یا حفاظ DB جلوی UPDATE/DELETE دفترها و محتوای سند قطعی را بگیرد.

هر فرمان حساس idempotency_key داشته باشد. یک کلید با payload یکسان نتیجه قبلی را برگرداند؛ همان کلید با payload متفاوت خطای conflict بدهد. داخل تراکنش کوتاه BEGIN IMMEDIATE، قیمت/نسخه/موجودی/تخصیص را دوباره بررسی کن، سند و تمام دفترها و نتیجه فرمان را بنویس و یک‌بار commit کن [۴]. در هر خطا rollback کامل؛ چاپ، سخت‌افزار و backup داخل تراکنش نباشند.

پس از قطع پاسخ، کلاینت همان کلید را استعلام/تکرار کند؛ دکمه دوباره سند تازه نسازد. busy خطای قابل فهم و retry محدود همان فرمان داشته باشد. رفتار transaction واقعی SQLAlchemy/SQLite را با نسخه Python انتخابی آزمایش کن؛ به پیش‌فرض driver تکیه نکن [۵].

۸ فروش و تغییر قیمت

اسکن بارکد یا جست‌وجوی نام، ورود مقدار، نمایش مبلغ، انتخاب پرداخت و تأیید نهایی در یک صفحه باشد. اسکن مجدد کالای تعدادی تعداد را زیاد کند؛ کالای وزنی پنجره مقدار باز کند. قیمت پیش‌نویس همراه نسخه ذخیره شود. اگر هنگام ثبت قیمت عوض شده، سرور اختلاف را نشان دهد؛ کاربر قیمت جدید را قبول کند یا مدیر قیمت قبلی را با علت تأیید کند. قیمت مخفیانه تغییر نکند.

دو تب می‌توانند یک موجودی را ببینند؛ فقط ثبت اول موجودی را مصرف می‌کند و ثبت دوم کمبود روشن می‌گیرد. قیمت، تخفیف، جمع و موجودی ارسالی مرورگر معتبر فرض نشوند. برای نسیه، مشتری مشخص الزامی است. فروش نقدی بدون Party مجاز؛ نام «مشتری متفرقه» محل انباشت نسیه نباشد.

۹ خرید و ورود اولیه

خرید شامل تأمین‌کننده، شماره فاکتور خارجی اختیاری، کالا، مقدار و بهای خالص است؛ پرداخت کامل/بخشی/بعدی مستقل ثبت شود. شماره تکراری تأمین‌کننده هشدار بدهد. کالای جدید خودکار از متن بارکد ساخته نشود.

موجودی اول دوره با مقدار و ارزش مشخص، بدهی اول دوره هر طرف و مانده اولیه صندوق/بانک اسناد جدا دارند؛ نباید فروش یا سود محسوب شوند. اصلاح شمارش انبار فقط مدیر، با مقدار شمارش‌شده و دلیل؛ کاهش با میانگین جاری و افزایش با بهای صریح تأییدشده. ضایعات هزینه/کاهش موجودی جدا از بهای فروش است.

انقضا در فاز دو محدود باشد: expiry_date اختیاری ردیف خرید و فهرست بررسی دستی تاریخ‌های نزدیک؛ expiry_reviewed_at و reviewer ثبت شود. این فهرست ادعای موجودی باقی‌مانده هر سری ساخت ندارد؛ انبار بچ‌محور و FEFO خارج از نسخه اول‌اند.

۱۰ پرداخت و نسیه

تسویه بخشی و چندروش مجاز است. پرداخت نقدی، کارت دستی و واریز بانکی جدا باشند. مجموع مبلغ دریافت‌شده‌ای که به فاکتور تخصیص می‌یابد از مبلغ قابل‌تسویه بیشتر نشود. پول تحویلی نقد و باقیمانده مشتری در UI نمایش داده شوند؛ گردش صندوق فقط مبلغ خالص دریافتی است. طلب، بدهی و اعتبار قابل‌استرداد هر شخص جدا نمایش داده شوند؛ تهاتر اشخاص مختلف ممنوع است.

ثبت فاکتور نسیه AR ایجاد می‌کند؛ دریافت بعدی با Payment و Allocation همان AR را کم می‌کند. خرید AP ایجاد می‌کند؛ پرداخت تأمین‌کننده فقط AP و پول را کم می‌کند. دفتر شخص باید سند، تسویه، برگشت و مانده قابل پیگیری نشان دهد. گرفتن پیش‌دریافت نامرتبط با بدهی در نسخه اول ممنوع است.

کارت دستی فقط پس از مشاهده موفقیت روی دستگاه/رسید توسط صندوقدار ثبت شود؛ وضعیت confirmed_manual و «نیازمند تطبیق» از تأیید بانکی تفکیک شود. مبلغ به card_clearing می‌رود؛ انتقال بعدی به bank درآمد مجدد نیست. وضعیت unknown/pending نه موفق است نه مجوز شارژ دوباره؛ پیش‌نویس را نگه دار و تطبیق دستی بخواه. فروش نسیه به‌جای پرداخت نامعلوم فقط با انتخاب صریح کاربر و مشتری مشخص مجاز است.

۱۱ مرجوعی

مرجوعی فروش باید به ردیف فروش اصلی وصل باشد؛ مجموع مقدار برگشتی از مقدار اصلی بیشتر نشود. مبلغ اعتبار و هزینه برگشتی از snapshot همان فروش است. برای برگشت‌های متعدد، مقدار هر نوبت را با روش تجمعی محاسبه کن: ROUND_HALF_UP(original_total × cumulative_return_qty / original_qty) منهای مجموع مبالغ برگشتی قبلی؛ همین روش برای cost_rial. برگشت کامل دقیقاً مبلغ و بهای اصلی را معکوس می‌کند.

کالای سالم به موجودی برگردد. کالای خراب ابتدا با بهای اصلی برگشت و سپس با یک حرکت ضایعات مرتبط همان بهای برگشتی خارج شود؛ ارزش ضایعات جدا گزارش شود. اعتبار مرجوعی اول بدهی باز همان فاکتور را کاهش دهد؛ تخصیص به بدهی دیگر همان مشتری فقط با نمایش و تأیید. باقی اعتبار، refund_due است و پس از بازپرداخت واقعی نقد/بانک صفر می‌شود. قول بازپرداخت را به‌عنوان پول پرداخت‌شده ثبت نکن. مرجوعی فروش نقدی بی‌نام با بازپرداخت کامل همان لحظه PartyEntry لازم ندارد؛ نگهداری اعتبار یا بازپرداخت بعدی فقط با مشتری مشخص مجاز است.

در مرجوعی خرید، اعتبار تأمین‌کننده از قیمت خرید اصلی محاسبه شود، اما خروج موجودی با میانگین جاری باشد. اختلاف «اعتبار خرید منهای ارزش خروج» به‌عنوان purchase_return_variance جدا گزارش شود؛ آن را وارد سود ناخالص فروش نکن. ابتدا AP سند اصلی کاهش یابد؛ مازاد طلب از تأمین‌کننده است تا پول واقعاً دریافت شود. خروج بیش از موجودی و برگشت بیش از خرید اصلی ممنوع است.

۱۲ صندوق و گزارش‌ها

صفحه خلاصه: فروش خالص، سود ناخالص، دریافت نقد، کارت ثبت‌شده/تطبیق‌نشده، هزینه، مانده صندوق، طلب مشتری، بدهی تأمین‌کننده و کمبود موجودی. بازه تاریخ و لینک تا سند اصلی داشته باشد. گزارش موجودی مقدار/ارزش، کارت کالا، دفتر شخص و خروجی CSV با محافظت از formula injection لازم است.

سند expense دسته‌بندی و مبلغ دارد و بدون حرکت انبار، هزینه را یک‌بار شناسایی می‌کند؛ بخش پرداخت‌شده گردش پول و بخش پرداخت‌نشده با طرف مشخص AP ایجاد کند. تسویه بعدی هزینه مجدد نیست. انتقال بین حساب‌ها یک رویداد اتمیک با دو MoneyMovement برابر و مخالف، بدون PartyEntry و سود است؛ آورده/برداشت مالک category مستقل دارند.

بستن روز، وجه نقد مورد انتظار و شمارش نقد واقعی را مقایسه و مغایرت را ثبت کند؛ کارت و تسویه بانکی جدا گزارش شوند. مغایرت خودکار فروش نشود. نسخه اول ثبت با تاریخ گذشته ندارد؛ accounting_date از زمان ثبت تهران گرفته شود و تاریخ چاپی فاکتور تأمین‌کننده فیلد اطلاعاتی جداست. ترتیب قطعی posting مبنای ارزش‌گذاری است. پس از بستن، ثبت ممنوع؛ بازگشایی فقط برای همان روز جاری توسط مدیر با علت و audit. گزارش روزهای گذشته فقط خواندنی است. برداشت مالک و انتقال بین حساب‌ها از هزینه عملیاتی جدا باشند. وجه نقد و bank نباید با پرداخت از مانده موجود منفی شوند.

۱۳ فارسی و زمان

RTL، فونت محلی، اعداد خوانا و میانبرهای واضح لازم است. ارقام فارسی/عربی به ASCII برای پردازش تبدیل شوند؛ نام برای جست‌وجو با ی/ي و ک/ك یکسان‌سازی شود، متن اصلی حفظ شود. بارکد رشته مستقل است؛ صفر ابتدایی، طول و check digit احتمالی بی‌دلیل تغییر نکند. مبلغ، مقدار و واحد کنار هم باشند.

زمان رخداد UTC؛ accounting_date تاریخ میلادی محلی فروشگاه در Asia/Tehran و نمایش شمسی باشد. کتابخانه تبدیل شمسی و داده منطقه زمانی بسته‌بندی شود؛ UTC+3:30 را دستی ثابت نکن. مرز روز، سال کبیسه شمسی و تغییر ساعت سیستم آزمون داشته باشد.

رسید HTML فارسی با شماره، تاریخ، اقلام، مقدار/واحد، تخفیف، جمع و روش پرداخت بساز؛ CSS چاپ A4 و عرض قابل تنظیم ۵۸/۸۰ میلی‌متر. چاپ دوباره فقط نسخه رسید است و فروش دوباره نمی‌سازد. پشتیبانی عملی چاپ حرارتی فارسی فقط بعد از آزمایش فیزیکی مدل دستگاه تأیید شود.

۱۴ قرارداد سخت‌افزار

ScaleAdapter.read_stable_weight() باید وزن صحیح، واحد، stable، timestamp و خطا برگرداند. وزن ناپایدار/قدیمی/منفی، قطع کابل و tare مشخص باشد؛ وزن نهایی را صندوقدار تأیید کند. BarcodeAdapter در آغاز همان USB keyboard wedge است؛ بارکد وزنی لیبل‌ترازو فقط با الگوی مستند قابل تنظیم پشتیبانی شود.

PaymentTerminalAdapter.start/status/cancel فقط قرارداد و mock است. mock روی DB آزمایشی و با برچسب دائمی «آزمایشی؛ پرداخت واقعی انجام نمی‌شود» کار کند و نتواند پرداخت واقعی را موفق اعلام کند. اجرای واقعی نیازمند SDK/پروتکل، مجوز ارائه‌دهنده و محیط آزمون است؛ اتصال USB به‌تنهایی کافی نیست. timeout هرگز مجوز تکرار برداشت نیست. PrinterAdapter نمونه HTML دارد؛ SDK/ESC-POS بعداً و بدون ادعای تضمین فارسی افزوده شود.

۱۵ امنیت و نگهداری

مدیر در اجرای اول گذرواژه خودش را بسازد؛ حساب/گذرواژه پیش‌فرض، secret ثابت و auth دورزدنی ممنوع. Argon2id یا روش استاندارد معتبر با کتابخانه نگهداری‌شده، session تصادفی سمت سرور با hash و انقضا، HttpOnly و SameSite=Strict؛ برای HTTP محلی Secure cookie را کورکورانه فعال نکن. خروج و غیرفعال‌کردن کاربر session را باطل کند.

صندوقدار: فروش، چاپ و مشاهده محدود؛ مدیر: قیمت، خرید، هزینه، مرجوعی، تعدیل، بستن/بازگشایی، گزارش سود و restore. مجوز هر route سمت سرور کنترل شود. CSRF token و بررسی Origin برای فرمان‌های تغییردهنده، محدودسازی Host به نشانی محلی/پورت مجاز، CORS بسته، CSP محلی، escaping قالب و جلوگیری از path traversal لازم است. GET هیچ تغییر مالی ندهد.

SQLite عادی رمزگذاری‌شده نیست؛ دسترسی فایل تابع حساب Windows است و backup اطلاعات خصوصی دارد. امنیت در برابر مدیر سیستم یا بدافزار تضمین نشود. logها چرخشی و بدون رمز/session/اطلاعات کارت باشند. هیچ دانلود یا بروزرسانی خودکار ناشناخته‌ای اجرا نشود.

۱۶ پشتیبان و بازیابی

از SQLite Backup API، مثلاً sqlite3.Connection.backup، snapshot سازگار بساز [۶]؛ کپی تنها فایل DB درحالی‌که WAL فعال است مجاز نیست. روزانه پس از بستن و پیش از migration نسخه تاریخ‌دار محلی بساز؛ امکان کپی همان snapshot به USB/دیسک خارجی فراهم کن. پیشنهاد نگهداری ۱۴ روزانه و ۸ هفتگی؛ حذف قدیمی فقط پس از موفقیت نسخه جدید. نبود مقصد خارجی، پرشدن دیسک یا شکست checksum هشدار روشن دارد؛ backup همان دیسک حفاظت از خرابی دیسک نیست.

manifest شامل app/schema version، زمان، اندازه و SHA-256 باشد. snapshot را با integrity_check و foreign_key_check بررسی کن. دکمه آخرین backup و تاریخ آخرین آزمون restore را نشان بده؛ گرفتن فایل به‌تنهایی اثبات بازیابی نیست.

restore فقط مدیر با تأیید روشن: موقتاً نوشتن متوقف، connectionها بسته، DB فعلی حفظ و نسخه ایمنی گرفته شود. فایل منتخب ابتدا در مسیر جدا validate شود؛ schema جدیدتر از برنامه رد شود و schema قدیمی فقط روی کپی با migration پشتیبانی‌شده ارتقا یابد. پس از آزمون جمع موجودی/ارزش/AR/AP/پول، جایگزینی امن و startup مجدد؛ شکست باید DB قبلی را قابل برگشت نگه دارد. sessionها پس از restore باطل شوند و تراکنش‌های واقعی کارت از زمان backup نیازمند تطبیق دستی باشند. هیچ sync مستقیم فایل زنده با فضای ابری نساز.

۱۸ آزمون و شرط تحویل

آزمون unit برای ارقام/واحد/Decimal/تخفیف/گردکردن؛ integration روی SQLite فایل‌محور واقعی؛ آزمون رابط فروش تا رسید. فقط in-memory کافی نیست. موارد اجباری: دو تب و آخرین موجودی؛ قیمت تغییرکرده؛ دوبارکلیک؛ قطع پاسخ بعد از commit؛ crash قبل/بعد commit؛ قفل DB؛ دیسک پر؛ کارت unknown؛ قطع چاپگر؛ پرداخت بخشی و چندروشی؛ تکرار مرجوعی؛ صفر/منفی/overflow؛ تعداد کسری؛ وزن حد دقت؛ تاریخ بسته؛ عبور غیرمجاز نقش؛ CSRF؛ backup هم‌زمان فروش؛ restore خراب/قدیمی/جدید و migration ناموفق.

در هر شکست، نتیجه باید «همه تغییرات یا هیچ‌کدام» باشد و retry همان کلید دوباره پول/موجودی نسازد. invariantها را بعد از توالی تصادفی عملیات آزمایش کن: جمع StockMovement برابر StockBalance؛ مانده بدهی برابر اسناد/تخصیص؛ مجموع پول برابر MoneyMovement؛ برگشت از اصل بیشتر نباشد؛ موجودی صفر ارزش صفر؛ برگشت کامل بهای اولیه را دقیقاً برگرداند.

PyInstaller ترجیحاً onedir با launcher یک‌کلیکی و shortcut بساز. بسته Windows باید روی Windows ساخته و روی دستگاه پاک بدون Python و بدون اینترنت آزمایش شود [۷]. موفقیت آزمون Linux به معنی تأیید بسته Windows نیست. آپدیت برنامه DB را پاک نکند؛ پیش از migration backup و مسیر بازگشت موجود باشد.

تحویل مخزن: source کامل، pyproject.toml، lockfile نسخه‌ها، migrationها، tests، fixture کاملاً ساختگی، README_FA با نصب/اجرا/توقف/آزمون/backup/restore، راهنمای کوتاه صندوقدار، PyInstaller spec و build script، LICENSE و فهرست مجوز وابستگی/فونت، STATUS.md شامل کار انجام‌شده/باقی‌مانده/اشکال شناخته‌شده. دستورات مستند مانند python -m app، alembic upgrade head و pytest باید واقعاً با پروژه منطبق و اجرا شده باشند.

قبل از افتتاح: یک روز آزمایش ساختگی، سپس فروش محدود با دفتر موازی، آزمون قطع برنامه و بازیابی روی کپی؛ تأیید صاحب فروشگاه برای واحد پول، رسید، وزن، نسیه و مرجوعی. انتقال به داده واقعی فقط بعد از موفقیت این دروازه‌ها و تهیه backup انجام شود.

۱۹ برآورد و اطلاعات موردنیاز

برآورد برنامه‌ریزی نیروی انسانی، نه تضمین زمان Codex: فاز صفر ۱۲–۲۰ ساعت؛ فاز یک ۴۰–۶۴؛ فاز دو ۴۴–۷۲؛ بسته‌بندی، آزمون و پایلوت ۲۴–۴۴؛ جمع ۱۲۰–۲۰۰ نفرساعت. اتصال ترازو حدود ۱۶–۳۲ و کارت‌خوان ۲۴–۶۰ ساعت اضافه، فقط در صورت وجود SDK/مستندات و دستگاه؛ نبودشان می‌تواند کار را متوقف کند. زمان یادگیری، اصلاح و آزمون انسانی با تولید سریع کد حذف نمی‌شود.

پیش از خرید سخت‌افزار این‌ها روشن شوند: Windows/مشخصات رایانه؛ شمار تقریبی کالاها؛ کوچک‌ترین وزن فروش زعفران؛ مدل/پورت/پروتکل ترازو؛ چاپگر و عرض کاغذ و درایور؛ نوع بارکدخوان؛ شرکت پرداخت و مدل کارت‌خوان/SDK؛ محل backup خارجی. برای ساخت هسته این پرسش‌ها مسدودکننده نیستند. برای اتصال واقعی و تأیید نهایی، پاسخ لازم است.

۲۰ منابع رسمی برای سازنده

این منابع در زمان تهیه بررسی شده‌اند؛ نسخه‌ها و سازگاری را هنگام ساخت دوباره بررسی کن. قواعد کسب‌وکار و برآورد زمانی این سند تصمیم طراحی پروژه‌اند، نه ادعای این مستندات.

[۱] SQLite، موارد استفاده و محدودیت نویسندگی:
https://www.sqlite.org/whentouse.html
[۲] SQLite PRAGMA، foreign_keys، synchronous، journal_mode و busy_timeout:
https://www.sqlite.org/pragma.html
[۳] Python Decimal:
https://docs.python.org/3/library/decimal.html
[۴] SQLite Transactions و BEGIN IMMEDIATE:
https://www.sqlite.org/lang_transaction.html
[۵] SQLAlchemy SQLite و کنترل تراکنش؛ Alembic migrations:
https://docs.sqlalchemy.org/en/20/dialects/sqlite.html
https://alembic.sqlalchemy.org/en/latest/tutorial.html
[۶] SQLite Backup API و Python sqlite3:
https://www.sqlite.org/backup.html
https://docs.python.org/3/library/sqlite3.html
[۷] PyInstaller، نحوه بسته‌بندی و ساخت برای سیستم‌عامل هدف:
https://pyinstaller.org/en/stable/operating-mode.html
https://pyinstaller.org/en/stable/usage.html
FastAPI، اجرای سرور و قالب‌ها:
https://fastapi.tiangolo.com/deployment/manually/
https://fastapi.tiangolo.com/advanced/templates/

دستور پایانی به عامل کدنویسی: از فاز صفر شروع کن، قواعد پول/موجودی و سناریوهای عددی را اول به آزمون تبدیل کن، سپس برش‌های کوچک قابل اجرا بساز. دامنه را بی‌اجازه گسترش نده، اتصال ناشناخته را mock و صریح علامت بزن، داده واقعی وارد نکن و فقط چیزی را آماده اعلام کن که شواهد آزمونش را داری.
